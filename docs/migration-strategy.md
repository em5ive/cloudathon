# Enterprise migration and data-center exit

The business objective is to exit the old virtualization platform and data center before the Q4 2027 lease expiration, while reducing licensing exposure and protecting retail operations. Exact lease and license notice dates are unknown. Use **September 30, 2027** as the conservative exit deadline until procurement confirms the contract; aim to complete production cutovers by **August 31, 2027**. The Cloudathon app is one representative modernization POC, not the migration of hundreds of VMs.

## Repeatable process

1. **Discover and reconcile.** Export server inventory from the actual platform/CMDB, collect OS/version, vCPU/RAM/storage, utilization over representative peaks, application owner, criticality, data classification, interfaces and observed dependencies. Record virtualization, OS, DB and application entitlements separately, plus contract renewal/termination dates. Reconcile CMDB with network observations, backup inventories and owner interviews; silent batch jobs and quarter-end integrations need explicit review.
2. **Classify by application.** Retire unused systems; retain only with an approved exit dependency; rehost stable supported VMs with limited change; replatform databases or middleware where compatibility is proven; refactor small independently owned services where value justifies effort. A commercial appliance or stateful legacy system need not become Lambda. Capture target, rationale, owner, license treatment, effort, RTO/RPO and rollback constraints.
3. **Build waves.** Group mutually dependent workloads and shared DBs into an application move group. Move identity, network, DNS, monitoring and backup foundations first. Use a dependency DAG for inter-group ordering; cycles require a combined group or an approved transitional link. Follow a noncritical pilot with repeatable 20–40 VM waves only after rehearsals establish capacity. Count applications and validated throughput as well as VMs.
4. **Automate the appropriate layer.** AWS Transform can assist discovery, dependency analysis, network planning and migration orchestration; MGN performs supported server replication/test launch/rehost into EC2. Terraform builds standardized target infrastructure, roles, subnets and approved application services. Terraform does not copy disk blocks or automatically convert business logic. Treat generated plans as reviewable artifacts, with human ownership of classifications, licenses and cutover gates. See [AWS Transform migrations](https://docs.aws.amazon.com/transform/latest/userguide/transform-app-vmware.html), [current discovery tool](https://aws.amazon.com/blogs/migration-and-modernization/introducing-the-aws-transform-discovery-tool/) and [MGN guidance](https://docs.aws.amazon.com/mgn/latest/ug/what-is-application-migration-service.html).
5. **Validate each move group.** Launch tests in isolated target networks; verify dependency connectivity, authentication, least privilege, TLS, backups and restore. Reconcile record counts/checksums and business totals, run representative retail journeys and load tests, and compare latency/error/resource baselines. Have application/data owners sign an evidence checklist. Validate patch/license activation and monitoring before cutover.
6. **Cut over with rollback criteria.** Announce the maintenance window, lower DNS TTL in advance where applicable, verify replication lag against the agreed RPO, freeze writes, drain jobs, take an approved recovery point, finish replication, switch traffic, and validate. Set an explicit observation window and objective rollback trigger. Before accepting target writes, rollback may redirect to a verified unchanged source. After target writes exist, stop writes and reconcile or reverse-replicate them before returning to source; never switch to a stale source and claim no data loss.
7. **Decommission and realize savings.** After signed acceptance and an agreed rollback-retention period, obtain deletion approval, archive required evidence/backups, remove legacy jobs/DNS/agents, retire VMs and host clusters, sanitize or return hardware, cancel eligible platform/facility contracts, and confirm final invoices. Retained rollback capacity has a cost and can delay license retirement. A powered-off VM alone is not a completed licensing exit.

MGN's staging resources, network paths, supported source OS versions, replication bandwidth, service quotas and production-account permissions must be checked before using it. No MGN agent, Transform job, replication instance or live discovery collector has been installed or launched by this POC. PostgreSQL modernization may need a separately assessed schema/data migration workflow rather than MGN's disk-level rehost. The reference MySQL infrastructure is not an existing company data source.

## Roadmap from November 2026

| Dates | Milestone and dependencies | Gate/risk/contingency |
| --- | --- | --- |
| Nov–Dec 2026 | Contract/license baseline, owner inventory, dependency observations, bandwidth and landing-zone design | Unknown owners, unsupported software and notice dates escalated by Dec 15. Confirm lease deadline and renewal windows. |
| Jan 2027 | Approved landing zone, identity/connectivity, logging/backup, migration tooling and representative POC | Quotas/permissions and security approval precede replication. Refine costs using measured sizes. |
| Feb 2027 | Pilot 10–20 low-risk VMs and one modernized application; rehearse restore and rollback | Measure days/application and bandwidth. Revise wave sizes; no hundreds-VM throughput claim from one POC. |
| Mar–Jun 2027 | Repeating dependency-aware production waves; rehost most deadline-critical legacy workloads | For the fictional 300-VM example, establish capacity of at least about 47 VMs/month across March–August. Use observed pilot throughput, parallel groups and license deadlines to set actual capacity. |
| Jul–Aug 2027 | Remaining critical/complex groups, final data and integration cutovers | Aim for all production off source by Aug 31. Freeze optional refactoring that threatens exit. |
| Sep 2027 | One-month contingency, rollback retention expiry, final decommission and facility handback | Finish required evidence and supplier cancellation before Sep 30. Any residual dependency has an executive owner and dated remedy. |
| Q4 2027 onward | Optimize rehosted workloads and modernize additional services after exit | No assumed lease extension or deferred core exit. |

The throughput figures are an **illustrative capacity plan**, not an inventory: a fictional 300-VM fleet needs approximately 20 pilot migrations plus six production months at **47 VMs/month** during March–August. Validate staffing, source connectivity and application groups by February. Scheduling only 30–40 per month early would create a risky 60-VM/month late surge; avoid relying on that catch-up. For a larger fleet, more parallel teams or earlier higher throughput are necessary. Keep at least a full month for contingency rather than scheduling routine waves to the lease deadline.

Critical risks are delayed licensing notices, missing application owners, database compatibility, insufficient network capacity, unsupported source OS, shared identity/filesystems, limited staff, data reconciliation failures and business blackout periods. Maintain a weekly dependency/decision log with owner and due date. Reserve fallback capacity: deadline-driven rehost to approved EC2 or a compatible hosted target can precede later refactoring; any remaining external facility contract or alternate target requires a separate business approval.

## Small executable automation demonstration

The repository's `scripts/discover-inventory.py` normalizes an **exported CSV** into dependency-aware candidate move groups and a review report; it does not discover real servers by itself or call a migration API. Run `python scripts/discover-inventory.py --inventory migration/inventory.example.csv --dependencies migration/dependencies.example.csv --output reports/migration-waves.csv`. Demonstrate the sample, then replace it with an authorized sanitized inventory export. Review unknown dependencies and every proposed classification; generated waves are recommendations.

An authorized fleet workflow is: export inventory → sanitize and reconcile → run the local inventory tool → obtain application-owner approval of move groups → enter approved groups into Transform/MGN → test launch → signed validation → authorized cutover → retention → separately approved decommission. Record source inventory hash/version, tool version, target Terraform commit, approved plan, test evidence and acceptance owner for every wave.

What is executable now: local inventory transformation, repeatable application packaging, Terraform definitions and local tests. The [MGN wave runbook](migration-wave-runbook.md) provides reviewed JSON-input command templates for a future authorized enterprise wave. What remains conceptual or blocked: live fleet discovery, Transform assessment, MGN replication and cutover, company financial validation, real license retirement and the production migration program. The POC's deployment is also blocked until account authentication and approvals exist.
